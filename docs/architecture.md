> Контракт API — `openapi-frontend.yaml` (v0.2.0), он источник истины. Здесь — обзор экранов и
> продуктовых решений. При расхождении верить YAML и обновлять этот файл следом за ним.

## 1. Стек

Vue 3 + TypeScript + Vite + Element Plus + Pinia + Vue Router + Vue Query (Tan Stack) + ECharts (графики есть что рисовать: показания канала из `/channels/:id/measurements`) + ~~Leaflet (карта)~~

Тестирование: Vitest + Vue Test Utils. Playwright — опционально.

Сборка: статика за Nginx.

## 2. Маршруты, данные и layout

**AppLayout:** Sidebar (навигация) + Header (уведомления, кнопка открытия формы, пользователь) + RouterView.

**AuthLayout:** только RouterView.

| Маршрут      | Страница             | Layout     | Данные                              |
| ------------ | -------------------- | ---------- | ----------------------------------- |
| /login       | Вход                 | AuthLayout | сессии ещё нет                      |
| /dashboard   | Аналитическая панель | AppLayout  | `prediction_log`                    |
| /predictions | Список прогнозов     | AppLayout  | `prediction_log`                    |
| /alarms      | Журнал срабатываний  | AppLayout  | `raw_events`                        |
| /objects     | Реестр объектов      | AppLayout  | `dim_objects` + актуальные прогнозы |
| /403         | Нет доступа          | AuthLayout | -                                   |
| \*           | 404                  | AuthLayout | -                                   |

**Карты не будет.** Координат в контуре Заказчика нет и не появится, привязка к местности
вынесена за рамки проекта, ручки `/map` из контракта убрана — вместо заглушки с пустым GeoJSON
честнее отсутствие ручки. Требование ТЗ разд. 10 закрывается списком объектов с уровнем риска:

    /objects — список объектов
    ├── level 1 — район по эксплуатации, 2 — комплекс, 3 — объект с каналами
    ├── risk = макс. уровень среди актуальных прогнозов (withRisk=true)
    └── клик → карточка объекта
        ├── прогнозы и срабатывания объекта
        └── лента истории /objects/:id/journal

Связь канал→объект в выданных данных есть: поле `ид_объект` в реестре каналов заполнено у 100%
каналов, поэтому прогноз и срабатывание отдаются с человекочитаемым контекстом объекта
(`context`), а не голым `targetRef`.

## 3. API

Сквозные правила (подробно — в комментариях YAML): даты ISO 8601 с зоной, всегда момент времени,
а не локальная дата; bigint-идентификаторы строками, потому что id событий доходят до 4.48 млрд,
а Number теряет точность после 2^53; интервалы `[from, to)` — нижняя граница включается, верхняя
нет; вероятность 0…1, проценты считает фронт; ошибки — `application/problem+json` (RFC 9457),
машинная ветвь по `status` и `type`; объект вне области видимости отдаётся 404, а не 403.

| Метод                             | Что                                                                                                      |
| --------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `GET /predictions`                | Список прогнозов, сортировка `computedAt DESC, id DESC`; `X-Total-Count` есть                            |
| `GET /predictions/:id`            | Карточка прогноза и все решения по нему для боковой панели                                               |
| `GET /alarms?from=&to=`           | Срабатывания: `from` и `to` обязательны, максимум 31 день; `X-Total-Count` нет → опора на `hasMore`      |
| `GET /alarms/:eventId?eventTs=`   | Карточка срабатывания; ключ строки — пара `eventId` + `eventTs`                                          |
| `POST /decisions` (с `requestId`) | Решение диспетчера, append-only; ветка `target.type = ALARM` пока отклоняется 400                        |
| `GET /objects?level=&withRisk=`   | Реестр объектов, `X-Total-Count` есть; `withRisk` принимается, но поле `risk` ещё не приходит            |
| `GET /objects/:id/journal`        | Лента объекта за интервал: прогнозы и срабатывания вперемешку, сортировка по `occurredAt`                |
| `GET /channels?objectId=`         | Реестр каналов (11 485 записей); `known=false` — канал есть в потоке, но отсутствует в реестре (ADR-014) |
| `GET /channels/:id/measurements`  | Показания канала за интервал: график по `numericValue`, лента состояний по `textValue`                   |
| `GET /reference-data`             | Справочники и пороги риска                                                                               |
| `GET /dashboard`                  | Сводка рисков по области видимости пользователя                                                          |
| `GET /notifications/stream`       | SSE критических прогнозов                                                                                |

`X-Total-Count` отдаётся только там, где COUNT дёшев: `/predictions`, `/objects`, `/channels`.
На ручках поверх таблицы срабатываний (`/alarms`, `/channels/:id/measurements`,
`/objects/:id/journal`) его нет — там сотни миллионов строк, счётчик стоит дороже самой выборки.

Счётчики дашборда считаются по актуальным прогнозам (`computedAt <= now < horizonUntil`), и в
них попадает только последний прогноз по сочетанию «цель + тип инцидента»: иначе повторные
расчёты одной цели покажут три проблемы там, где она одна. Общее число строк журнала отдаётся
отдельно как `predictionRows`, чтобы расхождение не выглядело ошибкой.

    GET /notifications/stream
    ├── fetch с ReadableStream (при cookie-сессии работает и нативный EventSource)
    ├── event: critical-predictions
    ├── data: PredictionPage (items, limit, offset, hasMore)
    ├── каждые 5 секунд, включая первый снимок сразу после подключения
    ├── replace state, не append
    ├── дедупликация уведомлений по prediction.id
    ├── reconnect через 5 секунд, нет Last-Event-ID
    ├── стрим живёт 30 минут, затем клиент переподключается
    ├── 503 — превышен лимит одновременных потоков
    └── авторизация — cookie сессии, заголовок Authorization не используется

Это снимок, а не гарантированная доставка: прогноз, который появился и истёк, пока вкладка была
отключена, отдельного уведомления не получит — он виден в журнале. Центр уведомлений с историей
пропущенного и отметками «прочитано» требует хранения на бэкенде и в контракт не входит.

Пагинация по offset не даёт стабильного снимка: журнал непрерывно дописывается. Для обновления
возвращаться на `offset=0`, а не листать дальше.

## 4. Авторизация

1. Вход через LDAP/AD (`POST /auth/login`): проверка учётных данных в каталоге, сессия кладётся
   в БД (spring-session-jdbc) и отдаётся cookie `SESSION`. Cookie HttpOnly, вне локальной
   разработки `Secure`. Токена в ответе нет: HttpOnly-cookie недоступна скрипту, а токен в
   localStorage забирается первым же XSS.
2. Все запросы идут с `credentials: include` (у axios это `withCredentials`, для SSE — потоковый
   fetch), иначе cookie не поедет. При кросс-доменной установке нужен CORS с credentials.
3. Каждый изменяющий запрос (POST) обязан нести `X-XSRF-TOKEN` со значением cookie `XSRF-TOKEN` —
   сервер выставляет её сам, и она читается скриптом намеренно: чужой сайт может заставить
   браузер послать cookie, но не может её прочитать. Без заголовка — 403. Исключение
   `/auth/login`, там сессии ещё нет.
4. До готовности LDAP на демо-стенде работает тот же путь с локальным списком пользователей —
   контракт не меняется, меняется только источник проверки.
5. Интерфейс строится по `permissions` из `GET /auth/me`, а не по `roles`: набор ролей будет
   меняться вместе с группами каталога, набор действий — нет. Бэкенд всё равно проверяет право
   на каждом вызове, ответ этой ручки разрешением не является.
6. `401` — сессии нет или она истекла. `403` — сессия есть, но не хватает права: повторный вход
   не поможет, роль выдаёт администратор каталога (ADR-027), и вести пользователя надо не на
   форму входа, а на объяснение. Как показывать 401 (объяснение или редирект на `/login` с
   сохранением `?redirect=`), в контракте не оговорено — согласовать и зафиксировать здесь.

## 5. Справочники

    GET /reference-data при старте
    ├── reasons → выпадающий список причин решения
    ├── incidentTypes → фильтр по типам (типы из журнала прогнозов, не полная таксономия модели)
    ├── riskThresholds → пороги medium / high
    └── predictionStatuses → NEW / REVIEWED

Поля «действия» (`actions`) в справочнике больше нет: решение описывается только причиной, а ось
«подтверждено или ложно» уже зашита в коды причин. Справочник причин целиком наш (ADR-022),
живёт в миграции и меняется только ею, порядок — по `code`.

Пороги 0.4 / 0.7 — условные значения для демо, не проверенные границы опасности. Отдаются в
`/reference-data`, чтобы фронт не зашивал их у себя; `riskLevel` считает бэкенд по этим порогам,
на фронте его не пересчитывать.

## 6. Экраны

### 6.1 Список прогнозов

Шапка: сводка из `/dashboard`.

Таблица: тип, вероятность, горизонт, цель, риск, статус, время, последнее решение.
`lastDecision` отдаётся прямо в списке, чтобы журнал не дёргал карточку по каждой строке.

Фильтры: период `[from, to)`, объект, тип инцидента, минимальная вероятность, статус, только
активные. Отдельного фильтра по уровню риска в контракте нет: риск задаётся порогом
вероятности, порог берётся из `riskThresholds`.

Пагинация серверная, число страниц — из `X-Total-Count`.

Паттерн:

→ клик по строке
→ боковая панель с карточкой прогноза + история решений
→ кнопка «Создать решение»
→ модалка с формой

### 6.2 Журнал срабатываний

Таблица: `eventId`, `eventTs`, объект и канал из `context`, значение (`rawValue` как пришло из
источника, плюс типизированные `numericValue` / `textValue`), статус, последнее решение.

Фильтры: период (обязателен, максимум 31 день), объект, канал. Полей `isAlarm` и `hasConflict`
в контракте нет: срабатывание — это уже событие с `тревожное = t`, а отдельного журнала ОДС в
выданных данных нет (ADR-010), источник тот же поток измерений.

Пагинация обязательна (сотни миллионов строк) и без общего числа: `X-Total-Count` на этой ручке
не отдаётся, поэтому «дальше/назад» по `hasMore` вместо номеров страниц.

Ключ строки — пара `eventId` + `eventTs`. Одного `eventId` недостаточно: он не уникален
(в 2021 повторяется 775 099 раз) и переиспользуется между годами. Оба поля таскаем вместе
до запроса карточки.

Паттерн:

→ клик по строке
→ боковая панель с карточкой срабатывания + история решений + ход показаний канала
→ кнопка «Создать решение»
→ модалка с формой

### 6.3 Карточка датчика вместо карты

Точек на карте нет; датчик живёт в реестре каналов и открывается из списка объектов.

→ клик по объекту в `/objects`
→ боковая панель: карточка объекта, его каналы (`/channels?objectId=`), лента истории
→ выбор канала → `/channels/:id/measurements`: график по `numericValue`, состояния по
`textValue`, `alarmOnly` — только тревожные
→ прогноз или срабатывание из ленты → карточка с историей решений

## 7. Форма решения диспетчера

- решение по прогнозу — можно, ветка `target.type = PREDICTION` реализована;
- решение по срабатыванию — по замыслу можно, но бэкенд пока отклоняет `ALARM` с 400: журнала
  событий наружу ещё нет, и ссылаться решению не на что. Экран `/alarms` — блокатор, начинать
  не с этой ветки;
- решение по нетревожному срабатыванию — **нельзя**.

Кнопка «Создать решение» гейдится правом `DECISION_CREATE`.

Состав формы — только причина и свободный комментарий:

- `reasonCode` обязателен, код из `/reference-data`; неизвестный код отклоняется, а не пишется
  как есть. Исход закодирован в самой причине: `CONFIRMED_INCIDENT` (подтверждён, направлен
  наряд), `FALSE_ALARM_EQUIPMENT`, `FALSE_ALARM_WORKS`, `MONITORING` (взято на контроль),
  `ESCALATED`.
- `comment` обязателен, когда у причины в справочнике `commentRequired === true` (исторически
  это `OTHER`), максимум 4000 символов.
- Поля `actionCode` нет: ось «подтверждено или ложно» уже есть в кодах причины, второе поле
  избыточно, и контракт следует за схемой, а не наоборот.
- `decidedBy` клиент не задаёт — сервер берёт логин из сессии, иначе разметка для дообучения
  перестаёт быть доверенной.

Идемпотентность:

- `requestId` (UUID) генерирует фронт один раз на сессию формы; при ретрае — тот же UUID и то
  же тело. Бэкенд отдаёт 200 с исходной записью, поэтому двойной клик и повтор по таймауту не
  создают второго решения.
- Другое тело с тем же `requestId` → 409.
- Новый `requestId` при повторной отправке → дубль, и append-only история их уже не различит.
- Ограничение текущей схемы: колонки `request_id` в init-схеме ещё нет (HACK-29), нужен
  отдельный changeset. UI на 200/409 закладываем уже.

История решений append-only: пересмотр добавляет запись, предыдущие не переписываются. Решение
и запись аудита (ADR-023) пишутся одной транзакцией. После успешной отправки статус прогноза
становится `REVIEWED`, что значит «решение зафиксировано», а не «инцидент устранён»; простое
открытие карточки статус не меняет.

### Что НЕ делаем сейчас

- Карту — координат нет, требование ТЗ закрывает список объектов с уровнем риска.
- Графики по модели и прогнозам — не по чему рисовать; график показаний канала — делаем.
- Рекомендации по обслуживанию и статусы заявок (ТЗ разд. 6) — источника таких данных в контуре
  нет. Причина «подтверждённый инцидент, направлен наряд» фиксирует решение диспетчера и
  НЕ создаёт заявку.
- Центр уведомлений с историей пропущенного и отметками «прочитано» — SSE-снимок этого не даёт.
- Отдельный журнал ОДС — не отделён (ADR-010).
- Админку, импорт — следующий этап.

Снято из старых ограничений: связь канал→объект есть, `ид_объект` заполнен у 100% каналов.
Открытым остаётся единица прогноза (ADR-003): третий уровень иерархии смешивает подсистемы и
отрезки коллектора, поэтому контракт не обещает, что любой прогноз относится к объекту — цель
описывается парой `targetKind` + `targetRef`, контекст объекта отдаётся, когда он выводим.
