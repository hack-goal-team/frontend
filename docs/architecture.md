# Архитектура интерфейса

Документ описывает реализованное приложение в `src/`. Контракт HTTP API
хранится в `backend/docs/openapi-frontend.yaml`; спецификация запущенного
Java-приложения доступна через `/v3/api-docs` и `/swagger-ui.html`.

## Состав

`src/app/main.ts` создаёт Vue-приложение, подключает Pinia, Vue Router и
TanStack Vue Query. Если в режиме разработки задано `VITE_USE_MOCK=true`,
до запуска приложения включается MSW. Код разделён следующим образом:

- `src/pages/` — страницы;
- `src/modules/` — API, типы, запросы и состояние предметных областей;
- `src/shared/api/` — общий HTTP-клиент, cookie и CSRF;
- `src/mocks/` — ответы для автономной разработки;
- `src/app/layouts/` — оболочки страницы входа и защищённых страниц.

Серверные списки и карточки загружаются через Vue Query. Пользователь,
справочник и уведомления хранятся в Pinia. Интерфейс читает готовые прогнозы
через бэкенд и не вызывает модель напрямую.

## Маршруты

| Путь                     | Страница                          | Право             |
| ------------------------ | --------------------------------- | ----------------- |
| `/login`                 | Вход                              | Публичный маршрут |
| `/dashboard`             | Сводка рисков                     | `PREDICTION_READ` |
| `/predictions`           | Журнал прогнозов                  | `PREDICTION_READ` |
| `/objects`               | Реестр объектов                   | `PREDICTION_READ` |
| `/objects/:id`           | Граф объекта                      | `PREDICTION_READ` |
| `/import`                | Загрузка журнала                  | `SETTINGS_WRITE`  |
| `/reports`               | Заглушка                          | `REPORT_READ`     |
| `/settings`              | Настройки: параметры и интеграции | `SETTINGS_WRITE`  |
| `/audit`                 | Журнал аудита                     | `AUDIT_READ`      |
| `/403`, неизвестный путь | Сообщение об ошибке               | Требуется сессия  |

Страж в `src/app/router/index.ts` получает профиль через `GET /auth/me`,
направляет пользователя без сессии на `/login?redirect=...` и проверяет
право для защищённого маршрута. Бэкенд повторно проверяет право и область
видимости каждого запроса; клиентская проверка управляет только навигацией.

## API и сессия

`src/shared/api/http.ts` создаёт Axios-клиент с `baseURL=VITE_API_URL` и
`withCredentials=true`. Для `POST`, `PUT`, `PATCH` и `DELETE` он добавляет
`X-XSRF-TOKEN` из cookie `XSRF-TOKEN`, если она есть. Импорт журнала
отправляется в `POST /admin/import/journal`; состояние задания читается
через отдельный запрос.

В карточке прогноза пользователь с правом `DECISION_CREATE` может создать
решение. Форма берёт причины из `/reference-data`, требует комментарий там,
где его требует причина, и отправляет `requestId` для идемпотентного повтора.
После успешного ответа обновляются запросы прогноза и сводки. Сейчас форма
создаёт решение только для цели типа `PREDICTION`.

Страница `/settings` читает параметры через `GET /settings` и сохраняет
через `PUT /settings`: срок действия решения, окно свежести показания и
пороги риска `MEDIUM`/`HIGH` (в контракте — вероятность 0…1, в форме —
проценты). Диапазоны контракта (`decisionCoverHours` 1…24, `sensorFreshHours`
1…720, целые часы) держит форма: `:min`/`:max` и `step-strictly`, иначе бэк
отвечает `400`. Горизонт прогноза отдаётся в ответе только для чтения. Блок
«Интеграции» запускает внеочередную загрузку данных из внешних систем:
`POST /admin/weather/refresh`, `/admin/river/refresh`, `/admin/registry/refresh`,
`/admin/ods/refresh`. Ручки синхронные, отвечают итогом загрузки; `409`
означает уже идущее обновление, `502` — недоступность источника. Каждый
вызов пишется в аудит на бэке. Строка реки дополнительно показывает последний
замер из `GET /river-level` (право не нужно, области видимости нет): уровень,
суточный перепад и время замера; `outdated=true` — замер старше `river.max-age`
(36 ч), его нельзя показывать как сегодняшний, поэтому рядом висит
предупреждение. После успешного `/admin/river/refresh` запрос уровня
инвалидируется.

Пороги риска живут только в `GET /reference-data`: фронт читает их через
`reference.thresholds` и не держит временных значений — пороги считает бэк, и переход
«Высокий риск» с панели и из индикатора критических ставит в фильтр журнала
`minProbability` именно из справочника. Поэтому сохранение порогов на `/settings`
обновляет справочник (`reload`), журнал прогнозов и сводку: `riskLevel` и `status`
пересчитываются и у прошлых строк. Без справочника порог HIGH неизвестен, и такой
переход не ведёт в журнал с выдуманным фильтром, а объясняет причину.

`predictionHorizonHours` оттуда же, из `GET /reference-data`: он объясняет ○ «без прогноза»
в реестре (`/objects`, `/objects/:id`) — прогноз считается на каждое событие канала, поэтому
событий не было ровно `N` часов. Подпись на записи дополняет тултип с этим `N`; без
справочника числа нет, и тултип не показывается, а не врёт «обычным» горизонтом.

Фильтры журнала прогнозов берут значения из того же справочника: «Тип инцидента» —
`incidentTypes` вида текущей вкладки, на бэк уходит `incidentType` (во вкладке «Оборудование»
тип один, фильтра там нет);
«Состояние» — `alarming=true|false` по `currentState.alarming`: `outdated` не учитывается,
прогнозы без `currentState` не попадают ни в один из вариантов; «Период» — `from`/`to` по
`computedAt`, снова `[from, to)`. Переходы с аналитической панели и из индикатора критических помечаются
параметром `nav`, а не `from`: `from` занят контрактом, и `from=dashboard` бэк прочитал бы
как дату.

Журнал разделён на вкладки «Инциденты | Оборудование» — `kind=INCIDENT|EQUIPMENT` в query
страницы и всегда в запросе `/predictions` (без `kind` бэк отдаёт смесь, `LEGACY` в интерфейс
не выводим). Вероятности двух моделей несопоставимы, поэтому шкалы не смешиваются. Колонка
«Класс» — `incidentType` с иконкой и подписью из `incidentTypes`; `context.incidentClass` —
класс датчика («Класс канала» у отказов, «Класс датчика» в карточке). У отказов `riskLevel`
двоичный: `HIGH` — «К проверке», порог `equipmentCheckThreshold` из `/reference-data` идёт
только в подсказку. `RiskTag` во вкладке «Оборудование» нет; ползунок «Мин. вероятность» тот же, что у инцидентов, и сбрасывается при смене вкладки. Смена
вкладки сохраняет период, состояние, статус и «только активные», остальное
сбрасывает. Число на вкладке — `X-Total-Count` (для соседней — запрос с `limit=1`). Все
переходы со сводки, из шапки и уведомлений ведут в `kind=INCIDENT`; карточка чужого вида,
открытая ссылкой, переключает вкладку сама.

Отказ датчика «к проверке» (`riskLevel=HIGH` у `EQUIPMENT`) виден и вне своей вкладки, но
заливку и счётчики инцидентов не меняет. В строке инцидента рядом с датчиком стоит 🔧, в карточке
информационная плашка «Датчик в зоне риска отказа» со ссылкой на прогноз отказа — по
`Prediction.equipmentRisk`. На графе — угловой значок узла по `Channel.equipmentRisk`: узел только
с отказом тоже кликабелен. На дашборде отдельная нейтральная карточка «Оборудование к проверке»
(`riskCountsByKind.EQUIPMENT.HIGH`); клик ведёт в отказы с `minProbability = equipmentCheckThreshold` —
у `EQUIPMENT` это ровно `HIGH`, фильтр виден на ползунке. В форме решения у отказа — подсказка про причину
`MAINTENANCE_REQUESTED` без предвыбора.

Страница `/audit` читает журнал через `GET /audit` (право `AUDIT_READ`, области
видимости нет, свежие сверху). Фильтры: `from`/`to` — интервал `[from, to)`, и
смещение уходит на бэк закодированным (`+03:00` → `%2B03:00`, иначе `+` станет
пробелом и `400`); `actor` — логин, точное совпадение; `category` — закрытый enum
(`AUTHORIZATION`, `DECISION`, `CHANGE_CONFIG`, `REPORT`, `IMPORT`); `action` —
повторяемый параметр (`?action=LOGIN_FAILED&action=ACCESS_DENIED` — любое из них)
с открытым набором кодов `^[A-Z][A-Z_]{0,63}$`, поэтому в фильтре разрешён ручной
ввод. Пустое значение параметра — без фильтра. Ответ — страница записей, тотальность
приходит заголовком `X-Total-Count`, навигация по страницам — как в журнале прогнозов.
`payload` — непрозрачная JSON-строка, раскрывается в строке таблицы как есть.

Обработка `401` при обычном API-запросе пока не перенаправляет браузер на
вход: в перехватчике оставлен TODO. Страж маршрута проверяет сессию при
навигации. Это ограничение следует учитывать при испытании истёкшей сессии
на уже открытой странице.

## Уведомления

`src/modules/notifications/useSse.ts` подключается к
`GET /notifications/stream` с cookie-сессией и принимает событие
`critical-predictions`. При переподключении обновляются запросы прогнозов,
сводки и карты рисков объектов. После ошибки или закрытия потока клиент
делает новую попытку через 5 секунд. Событие содержит снимок активных
прогнозов, а не гарантированную доставку каждого изменения.

Каждый новый id снимка показывается тостом «Подтопление · 94% / до 29.09 01:40 · объект /
датчик» (ТЗ :485). Первый кадр после входа тоже показывается тостами: диспетчер ещё не видел
активных HIGH. Если за раз пришло больше трёх, выводится один сводный тост «Высокий риск:
N инцидентов» с разбивкой по классам. Тост висит, пока его не закроют; клик ведёт в карточку
(`kind=INCIDENT&selectedId`), со сводного — как индикатор в шапке. Лента «Последние
уведомления» на панели использует тот же формат строки и тоже открывается первым кадром:
после входа её заполняет снимок целиком (не больше окна в 20 записей), дальше — только новые
id. Ждать одной дельты нельзя: бэк пересчитывает прогнозы не каждую секунду, и блок молчал
бы часами там, где тосты этот кадр уже показали.

## Конфигурация и сборка

`VITE_API_URL` задаёт базовый путь API; при совместном размещении —
`/api/v1`. В режиме разработки `VITE_API_TARGET` включает прокси Vite для
`/api`, если `VITE_USE_MOCK=false`. MSW работает только в dev-режиме.
`VITE_USE_MOCK_DELAY=false` отключает искусственную задержку ответов MSW.
`VITE_API_TOKEN` указан в шаблоне окружения, но HTTP-клиент его не читает.

`npm run build` запускает `vue-tsc -b` и Vite, результат находится в
`dist/`. Проверки: `npm run lint`, `npm run typecheck`,
`npm run format:check`, `npm run test:run`. Роутер использует History API;
веб-сервер должен возвращать `index.html` для путей приложения и
проксировать `/api/` к бэкенду. Для SSE на прокси отключают буферизацию.

## Ограничения реализации

Страница `/reports` показывает «Раздел в разработке». Отдельного маршрута
журнала срабатываний и кнопки запуска обучения в проверенном коде нет.
Карта местности не предусмотрена: исходный реестр не содержит координат.
Наличие маршрута `/objects/:id` означает граф объекта в интерфейсе, а не
географическую карту.
